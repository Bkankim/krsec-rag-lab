# 평가 규약 (eval-protocol v2)

이 문서는 실험보다 먼저 고정하는 평가 정의다(PLAN 원칙 4). 이후 모든 실험·베이스라인·골든셋 이슈는
이 문서를 정본으로 따른다. 항목마다 **판정**(하나를 고른 결과)과 **이유**를 적는다. 선택지를 늘어놓고
끝내지 않는다. 결과 파일에는 `protocol_version: "eval-protocol-v2"`을 남긴다. 단 #27 후보 산출물은 v1
그대로 두고, 교차 판정과 채점 결과만 v2를 쓴다(10절).

## 판정 요약

| 항목 | 판정 | 절 |

## 0. 전제

**판정**: 이 규약의 정의와 지표는 공개 메타데이터(`fixtures/kisa/metadata.jsonl`)의 필드 구조만 전제하고,
공지 본문은 전제하지 않는다. 본문을 읽는 일(8절 교차 판정, 5절 `no_answer` 부재 확인)은 로컬 캐시가 있는
환경의 판정·점검 단계에서만 하고, 그 결과는 본문 없이 ID·오프셋·고정 코드로만 남긴다.

**이유**: KISA 본문은 재배포 조건이 미확인이라 리포·로그·문서에 넣지 않는다(`LICENSES/README.md`).
규약은 본문 없이 쓸 수 있어야 하고, 이번 런의 자동 후보(#27)도 본문을 읽지 않는다.

공개 메타데이터 한 줄의 필드:

| 필드 | 형식 | 규약에서의 역할 |
|---|---|---|
| `nttId` | 문자열(5자리 숫자) | 문서 ID. 정답 단위의 키 |
| `cve_ids` | `CVE-YYYY-NNNN+` 목록(공지가 인용한 ID, 0개 이상) | CVE 질의의 정답 조인 키, 분할의 CVE 그룹 키 |
| `title` | 문자열 | 근접중복 판정(정규화한 제목) |
| `date` | `YYYY-MM-DD` | 근접중복 판정(게시일 간격) |
| `url` | 문자열 | 참조용 |

고정 fixture(2026-09-19 수집)의 실측 분포가 아래 판정의 근거로 쓰인다.

- 공지 50건, 이 중 CVE를 인용한 공지 41건, 없는 공지 9건.
- 인용 합계 1564건, 고유 CVE 1560개(4개가 공지 2건에 중복 인용).
- 한 공지가 996개, 다른 한 공지가 423개를 인용한다(정기 보안 업데이트 권고). 두 공지가 인용 합계의
  90.7%(1419/1564)를 차지한다. 나머지 공지는 대부분 1~18개를 인용한다.

표기: 문서 ID는 `nttId` 문자열, CVE ID는 대문자 `CVE-[0-9]{4}-[0-9]{4,}`로 정규화한다. CVE ID는 ASCII 숫자만 인식한다(전각·기타
유니코드 숫자는 CVE로 보지 않는다). 이 문서의 모든 예시는 합성이다(`d1`, `d2` 같은 가짜 문서 ID, `CVE-2026-0001` 같은 가짜 CVE).

표본이 작다(질의 수 수십~백 단위). 유형별 n이 10 미만이면 평균을 표시하되 우열 판정에는 쓰지 않고
`n`을 반드시 병기한다.

## 1. 정답 단위

**판정**: 채점 단위는 **문서(`nttId`)**다. 청크는 채점 단위가 아니고, 두 판정자가 지정한 근거 구간에서
파생하는 보조 단위다(8절). CVE ID는 정답 단위가 아니라 질의 판별 속성이자 조인 키다.

**이유**:

1. 청킹은 M3의 실험 변수다. 청크 단위로 정답을 고정하면 청킹 설정을 바꿀 때마다 정답 자체가 바뀌어
   "한 요소씩 바꾼다"(PLAN 원칙 2)가 깨진다. 문서 ID는 청킹·임베딩·검색 설정과 무관하게 불변이다.
2. CVE 단위로 채점하면 분포가 왜곡된다. 공지 2건이 인용 CVE의 90.7%를 차지하므로 CVE 단위 recall은
   사실상 그 2건의 회수율이 된다. CVE를 인용하지 않는 공지 9건은 CVE 단위로는 정답이 될 수 없다.
3. 이번 런의 자동 후보(#27)가 본문 없이 만들 수 있는 단위가 문서·CVE뿐이다. 문서 단위 판정이면
   후보를 그대로 채점 단위로 승격할 수 있고, 교차 판정(#10)은 후보를 확정·기각하거나 `unjudged`로 두는 일이 된다.
4. exact CVE-ID lookup 베이스라인이 "CVE -> 인용 공지" 인덱스로 문서 단위 순위를 직접 낸다. BM25·dense는
   청크를 검색하더라도 문서로 접으면 같은 단위로 비교된다.

Rejected: 청크 단위(위 1) | 청킹 변경 시 정답이 흔들림. CVE 단위(위 2) | 2개 공지가 지표를 지배.
혼합 점수(문서 점수와 청크 점수의 가중합) | 가중치가 숨은 변수가 되고 보고가 복잡해짐.

**정답 판정과 용어**: 정답은 사람 검수가 아니라 **두 판정자의 독립 교차 판정**으로 정한다. 판정자는 Anthropic
Opus 계열 1종(A)과 OpenAI GPT 계열 1종(B)이고, 서로의 결과를 보지 않고 질의-문서 쌍마다 판정한다. 관련성
라벨(relevant / not_relevant)이 일치한 것만 확정 후보로 삼고(정답이 되려면 둘 다 relevant여야 한다), 불일치와
kappa(8절)는 기록한다. 질문마다 문서는
셋 중 하나다.

| 용어 | 정의 |
|---|---|
| `gold` | 두 판정자 모두 relevant로 판정하고 근거 구간이 있는 문서(8절 3단계). 공개 트랙은 fixture 메타데이터로 기계적으로 정한 정답(11절) |
| `unjudged` | 판정 불가: 판정이 갈림, 재질의 뒤에도 근거 없음, 잘린 본문에서의 not_relevant, 공개 트랙의 CPE 절단 등 |
| 비관련 | 나머지. 잘리지 않은 본문에서 두 판정자가 모두 not_relevant로 일치한 문서, 그리고 판정 묶음 밖 문서 |

채점용 정답 집합 `G`는 질문의 `gold` 집합이다. 자동 조인 결과는 `G`가 아니라 **후보 집합**이다.

- CVE ID를 지정한 질의: 후보 집합 = 그 CVE를 `cve_ids`에 가진 공지 전부(질의가 CVE 여러 개를 지정하면
  합집합). 고정 fixture에서 4개 CVE는 후보가 2건이다. 각 후보는 교차 판정에서 `gold`, `unjudged`, 비관련 중
  하나가 되므로 `G`는 후보 집합의 부분집합이다(`|G| <= 2`).
- 그 밖의 질의: 교차 판정으로 확정한 `gold` 공지(1개 이상). 답 없음 질의는 `G = {}`이며 5절 규칙을 따른다.

**채점 전 처리 (condensed list)**: 아래 접기를 거친 문서 순위에서 해당 질문의 `unjudged` 문서를 지운 뒤(뒤 문서가
앞으로 당겨진다) 2~4절과 7절의 지표를 그대로 적용한다. 지표의 수식과 기대값은 바꾸지 않는다.

- `unjudged` 때문에 `gold`가 비게 된 질문은 채점에서 뺀다(`excluded`). `no_answer`로 바꾸지 않는다. 채점 제외는
  집계 제외다: `excluded` 질문은 dev/test 비율의 분모, `abstain_rate`·`false_abstain_rate`, `tie_at_cutoff@k`를
  포함한 모든 지표 집계에서 뺀다. 레코드는 질의셋에 남기고 건수만 보고한다. 보고에는 `n_scored`, `n_skipped`와
  함께 `n_excluded`를 적는다.
- condensed list는 **문서 관련성 순위 지표**(hit, recall, MRR, nDCG)에만 쓴다. 기권(7.3)은 `unjudged`를 지우기 전
  원래 1위 점수를 쓰고, ANN recall(4절)은 필터하지 않은 순위를 쓴다.

**한계**:

- 정답은 사람 검수가 아니다. 두 모델이 같은 방향으로 틀릴 수 있고, 일치는 정확성의 증명이 아니다. kappa는 두
  판정자의 일치 정도일 뿐 정답 품질이 아니다.
- KISA 트랙은 풀링 평가다. 판정 묶음 밖 공지는 비관련으로 간주하므로, 묶음 밖에 숨은 정답이 있으면 점수가
  낮게 나올 수 있다.
- 판정 구현 세부(판정자 프롬프트, 이유 코드, 호출 상한)는 이 문서에 쓰지 않는다. `eval/golden/judge_manifest.json`
  (#10)이 정본이고 이 규약은 그 파일을 가리키기만 한다.

**검색 결과 -> 문서 순위**: 검색기가 청크를 돌려주면 점수 내림차순으로 훑으며 문서마다 첫 등장만 남긴다
(문서 점수 = 그 문서 청크의 최고 점수). 이 접힌 목록에서 `unjudged`를 지운 목록이 문서 관련성 지표의 입력이다.
지운 뒤 길이가 k보다 짧을 수 있다(7절).

## 2. hit@k vs recall@k

질의 q, 문서 순위 `r`, 정답 집합 `G`(비어 있지 않음), `top_k` = 순위 앞 k개:

```
hit@k(q)    = 1 if |G ∩ top_k| >= 1 else 0
recall@k(q) = |G ∩ top_k| / |G|
```

**판정**: 둘을 모두 보고하되 이름과 용도를 분리한다. hit@k는 "생성기에 정답 근거가 하나라도 들어갔는가"
(컨텍스트 투입 기준), recall@k는 "정답을 전부 회수했는가"다. 보고하는 k는 {1, 5, 10}이다. hit@k를
recall이라 부르지 않는다. 가설 판정(PLAN 원칙 3)에 쓰는 **대표 지표(primary)는 nDCG@10**이고,
hit@1, hit@5, recall@10, MRR@10은 보조 지표다.

**이유**: 정답이 1개인 질의에서는 두 값이 같지만, `|G| >= 2`이면 갈린다(7절 B3: hit 1, recall 0.5).
이름을 섞으면 "정답 일부만 찾은 검색기"와 "전부 찾은 검색기"를 구분할 수 없다. 대표 지표를 하나로
정하는 이유는 가설마다 "개선됨/아님"을 한 숫자로 판정해야 하기 때문이고, nDCG@10을 고른 이유는 순위와
복수 정답을 둘 다 반영하면서 k 하나에 덜 민감해서다(hit/recall은 k 선택에 따라 결론이 뒤집힌다).

recall@k의 분모는 `|G|`로 고정한다(`min(|G|, k)`로 정규화하지 않는다). 표준 정의라 외부 구현과
교차검증(#12)이 되고, `|G| > k`이면 recall@k의 상한이 `k/|G|`임을 7절 B5가 고정한다.

## 3. MRR·nDCG (이진 라벨)

라벨은 이진이다. 문서가 `G`에 있으면 relevance 1, 아니면 0이다.

```
RR@k(q)   = 1 / rank_of_first_relevant   (그 rank <= k 일 때), 아니면 0
MRR@k     = RR@k의 질의 평균

DCG@k     = sum_{i=1..k} rel_i / log2(i + 1)
IDCG@k    = sum_{i=1..min(|G|, k)} 1 / log2(i + 1)
nDCG@k(q) = DCG@k / IDCG@k
```

**판정**: 이진 라벨, MRR은 k=10으로 절단(MRR@10), nDCG@10, gain은 `rel`(0 또는 1), 할인은
`1/log2(i+1)`(1위의 할인이 1)로 고정한다.

**이유**: 교차 판정 골든셋은 "근거가 있는 정답인가"만 판정한다. 등급(부분 정답 등)을 매기려면 등급 라벨에 대한
판정자 간 일치를 먼저 확인해야 하는데 지금 기록하는 일치(kappa)는 이진 라벨뿐이다. 이진 라벨에서는 gain을 `rel`로 쓰든 `2^rel - 1`로 쓰든
같은 값이라 구현 간 불일치 원인이 하나 줄어든다. MRR을 10에서 절단하는 이유는 nDCG@10과 같은 후보
깊이로 비교하기 위해서이고, 절단 없는 MRR은 100위 정답이 0.01을 더해 노이즈가 된다. `IDCG`의 상한을
`min(|G|, k)`로 두는 이유는 정답 수가 k보다 많아도 완벽한 순위가 nDCG 1.0을 받게 하기 위해서다.

## 4. ANN recall과 relevance recall

| 이름 | 정의 | 레이블 | 평균 대상 | 단위 |
|---|---|---|---|---|
| `ann_recall@k` | `\|ANN_k ∩ Exact_k\| / \|Exact_k\|` (Exact = 같은 벡터·같은 거리·같은 동점 규칙의 전수 검색) | 불필요 | 모든 질의(답 없음 포함) | 청크 ID(문서로 접기 전) |
| `recall@k` | 2절의 relevance recall | 필요(`G`) | 정답이 있는 질의만 | 문서 ID |

**판정**: 두 지표를 이름·계산 단위·평균 대상까지 분리해서 보고하고, 한 표에서 같은 이름으로 섞지 않는다.
실험 지표(relevance)는 **exact(전수) 검색으로 측정하는 것을 기본**으로 하고, HNSW 같은 근사 인덱스로
측정했다면 같은 표에 `ann_recall@k`를 병기한다. "ANN recall이 0.98이므로 검색 품질이 0.98"이라는
식의 서술을 하지 않는다.

**이유**: ANN recall은 "근사 인덱스가 전수 검색의 답을 얼마나 흉내 내는가"이고 정답 라벨과 무관하다.
relevance recall은 "전수 검색이든 근사든 정답을 찾는가"다. 두 값이 서로 다른 원인(인덱스 근사 손실 vs
임베딩·청킹·질의 적합도)을 재므로 섞이면 청킹이나 임베딩 효과에 인덱스 근사 손실이 끼어든다
(PLAN 원칙 2 위반). 코퍼스가 작아 전수 검색 비용은 무시할 수 있으므로 exact를 기본으로 두는 데 손해가 없다.

## 5. 질의 유형

| 유형(slug) | 정의 | 정답 `G` |
|---|---|---|
| `cve_explicit` | 질의 문장에 CVE ID가 있고 `G`가 비어 있지 않다 | 그 CVE(들)를 인용한 후보 공지 중 교차 판정으로 확정한(`gold`) 공지(1절) |
| `product_symptom` | 제품명·버전·증상을 서술해 "어느 공지가 해당하는가"를 묻는다 | 해당 공지(1개 이상) |
| `explanation_comparison` | 개념·조치 방법·공지 간 차이를 "무엇이/왜/어떻게/무엇이 다른가"로 묻는다 | 근거 공지(1개 이상) |
| `no_answer` | 코퍼스에 없음을 기계적으로 확인한 질의 (`G = {}`) | 없음 |

**판정**: 유형은 질의마다 정확히 하나이고, 아래 우선순위로 정한다.

1. `no_answer`는 코퍼스에 없음을 기계적으로 확인할 수 있는 질의로 한정한다. 예: 어느 공지의 `cve_ids`·제목에도
   없는 CVE ID를 묻는 질의. 판정 묶음의 판정이 모두 일치 not_relevant일 때 채택하고, 판정자가 갈리면 쓰지 않는다.
   표면에 CVE가 있었는지는 별도 속성 `surface_cve`(bool)로 남긴다.
   - 부재 확인(KISA 트랙): 고정 공지 전체의 정규화 본문·제목에서 `extract_cve_ids`로 확인한다. 메타데이터만으로
     확정하지 않는다. 기계적으로 부재를 확인하지 못했는데 `G`가 빈 질문(`no_answer` 후보)은 **폐기**한다. 폐기는 질의셋에
     넣지 않는다는 뜻이다.
   - `unjudged` 때문에 `gold`가 빈 질문은 `no_answer`가 아니라 `excluded`다(1절). `excluded`는 질의셋에 남기되
     채점·집계에서 뺀다. 폐기(질의셋에서 뺌)와 `excluded`(질의셋에 남김)를 섞지 않는다.
2. 문장에 CVE ID가 있으면 `cve_explicit`이다. 기계 판별식:
   `(?<![A-Za-z0-9])CVE-[0-9]{4}-[0-9]{4,}(?![0-9])`(대소문자 무시). `\b`를 쓰지 않는다: 한글 조사가 붙은
   `CVE-2026-12345를`에서 `\b`는 끝 경계를 찾지 못한다. `\d`도 쓰지 않는다: 유니코드 숫자(전각 등)까지 받기
   때문이다. 숫자는 ASCII `[0-9]`만 인식하고 유니코드 정규화(NFKC)는 하지 않는다(정규화하면 `CVE-2026-1234²`의
   위첨자가 숫자로 바뀌어 ID에 붙는다). 구현은 `splits.extract_cve_ids`다.
3. 그 밖에는 질의를 작성하는 단계에서 의도 테스트로 가른다. 답이 "어느 공지·제품인가"이면 `product_symptom`,
   "무엇·왜·어떻게·차이"이면 `explanation_comparison`이다.

**이유**: 지표의 정의역이 `G`의 공집합 여부에 달려 있으므로(7절) `no_answer`는 문장 모양이 아니라 `G`로
정해야 한다. 그런데 교차 판정에서 `G`가 빈 것은 "답이 없다"와 "판정이 모자라다"를 구분하지 못하므로, `no_answer`는
코퍼스에 없음을 기계적으로 확인한 질의로 좁힌다. 판정이 모자라 빈 질문은 `excluded`로 빼야 `no_answer`의 기권
점수가 오염되지 않는다. CVE 문장 판별은 기계 규칙으로 고정해야 유형 라벨이 판정자에 따라 흔들리지 않는다.
두 유형을 나누는 의도 테스트는 기계 규칙으로 쓸 수 없어 질의 작성 단계의 판단에 맡긴다. 이 구분은 검색 난이도가
다르기 때문이다(CVE 질의는 어휘 일치로 풀리고, 설명·비교 질의는 근거 구절이 필요하다).

**보고 규칙**: 지표는 유형별로 낸다. 정답이 있는 3개 유형을 합친 대표 값은 **유형별 평균의 단순 평균
(macro)**이다. 한 분할에서 어떤 유형의 채점 질의(`n_scored`)가 0건이면 그 유형은 macro에서 빼고, 분모는
채점 질의가 1건 이상인 유형 수다(0으로 세지 않는다). 질의 수로 가중한 평균은 보조로만 쓴다. 이유: CVE 질의는 쉽고 개수가 쏠리기 쉬워서 질의
수 가중 평균이 CVE 유형에 끌려간다(7절 평균 예시). `no_answer`는 별도 표로 보고한다(7절).

## 6. dev/test 분할

**판정**: 분할 단위는 **그룹 블록**이다. 질의를 무작위로 나누지 않고, 아래 세 종류의 그룹을 공유하는
질의는 같은 쪽에 둔다. 세 종류의 교집합이 dev와 test 사이에서 비어 있어야 하고, 이는 문서가 아니라
검사 코드(`src/krsec_rag_lab/splits.py`의 `assert_disjoint`)가 판정한다.

| 그룹 | 키 | 겹침의 의미 |
|---|---|---|
| 공지(`notice`) | 질의의 정답 공지 `nttId` | 같은 공지가 dev와 test 정답에 모두 있음 |
| CVE(`cve`) | 질의가 직접 적은 CVE + 정답 공지가 인용한 CVE (대문자 정규화) | 같은 CVE가 양쪽에 걸침(공지가 달라도) |
| 근접중복(`near_dup`) | 아래 판정 기준의 연결 성분. 정답 없는 질의는 정규화한 질의 문장 | 서로 다른 공지가 같은 묶음이거나, 같은 질문이 양쪽에 있음 |

**이유**: 누수는 질의 문장이 같아서가 아니라 질의가 기대는 근거가 같아서 생긴다. 같은 공지, 같은 CVE,
같은 템플릿의 연속 공지는 dev에서 맞춘 규칙(τ, 질의 재작성 규칙, 가중치)이 test 점수에 그대로 새어 들어가는
경로다. 질의 단위로 나누면 이 경로가 열려 있다. 또 분할의 정합성은 문서의 약속이 아니라 자동 검사로
지켜야 질의를 추가할 때마다 깨지지 않는다.

**근접중복 판정 기준** (코드 상수 `NEAR_DUP_WINDOW_DAYS = 14`):

- 두 공지는 **정규화한 제목이 같고** **게시일 간격이 14일 이하**이면 근접중복이다.
  정규화 = 유니코드 NFKC + 소문자화(casefold) + 연속 공백을 한 칸으로.
- 관계는 추이적으로 닫는다. A-B, B-C가 근접중복이면 A, B, C는 한 묶음이다(연결 성분).
- 질의 문장도 같은 정규화를 거쳐 문자열이 같으면 근접중복이다(정답 공지가 없는 질의를 위한 규칙).

**판정(14일)**: 창을 14일로 고정한다. **이유**: 고정 fixture에서 창을 바꾸며 센 결과가 아래와 같다.

| 창(일) | 묶음 수 | 2건 이상 묶음 | 그 묶음에 든 공지 |
|---|---|---|---|
| 7 | 50 | 0 | 0 |
| 14 | 45 | 3 | 8 |
| 21 | 41 | 6 | 15 |
| 30 | 36 | 10 | 24 |

30일이면 공지의 절반이 다중 구성원 묶음에 들어가 블록이 커져서 유형별 층화가 어려워진다. 7일은 아무것도
묶지 못해 근접중복 규칙이 무의미하다. 14일은 같은 벤더의 연속 권고를 묶으면서(예: 같은 제품명 공지가
8월 6일~9월 3일에 걸친 한 묶음) 블록을 작게 유지한다. 고정 fixture에서 같은 CVE를 공유하는 공지 쌍은
19일, 23일 간격이어서 14일 창에는 안 들어오지만, 이 쌍은 CVE 그룹 규칙이 막는다. 따라서 근접중복의
역할은 CVE를 공유하지 않지만 같은 템플릿을 쓰는 연속 권고를 막는 것이다.

한계(Not-tested): 같은 템플릿이라는 전제는 제목과 날짜로만 판정한 것이고 본문 유사도는 측정하지 않았다
(본문을 읽지 않는다). #10 교차 판정 결과에서 근접중복 묶음의 오탐·미탐 표본(같은 묶음 구성원의 판정이 갈리는지)을
점검하고, 오탐이 많으면 창이나 기준을 개정한다(10절).

**분할 절차** (질의 목록이 생긴 뒤, #10 몫):

1. 질의마다 그룹 키를 계산한다(`splits.group_keys`).
2. 세 종류 중 하나라도 키를 공유하는 질의를 한 블록으로 합친다(union-find).
3. 블록을 유형별로 층화하고 고정 시드로 배정한다. 목표 비율은 질의 수 기준 **dev 40% / test 60%**
   (±10%p 허용).
4. 배정 직후 `assert_disjoint`를 통과해야 한다. 통과하지 못한 분할은 쓰지 않는다.

**판정(비율)**: dev 40 / test 60. **이유**: test는 릴리스·가설 판정에 쓰는 최종 점수라 표본이 작을수록
불확실성이 커지므로 더 크게 잡는다. dev는 임계값 τ, RRF 가중치 같은 적은 수의 값을 고르는 데만 쓴다.

**사용 규칙**: 튜닝과 디버깅은 dev에서만 한다. test는 릴리스·가설 판정마다 한 번 실행하고, 결과를 본 뒤
규칙·임계값을 바꾸지 않는다(바꾸면 새 test 구성이므로 규약 개정이다). 코퍼스(색인 대상)는 분할하지 않는다:
dev와 test 모두 전체 문서를 색인에서 검색한다. 분할되는 것은 질의와 정답 라벨뿐이다.

Rejected: 질의 단위 무작위 분할 | 같은 공지·CVE가 양쪽에 걸려 dev 튜닝이 test 점수에 새어 들어감.
시간 순 분할 | 고정 fixture는 2개월 분량이고 같은 벤더 권고가 기간 전체에 반복되어 템플릿 누수를 못 막음.
K-fold 교차검증 | 가설마다 test를 한 번만 보는 원칙(PLAN 원칙 3)과 맞지 않고 질의가 수십 개라 폴드마다
유형별 표본이 바닥남.

검사 입력 형식(`#10`·`#27`의 레코드가 이 이름을 쓰거나 호출 전에 매핑한다):

```
item   = {"id": str, "split": "dev"|"test", "ntt_ids": [nttId...], "cve_ids": [CVE...], "query": str}
notice = {"nttId": str, "title": str, "date": "YYYY-MM-DD", "cve_ids": [CVE...]}   # metadata.jsonl 한 줄
```

`ntt_ids`, `cve_ids`, `query`는 생략할 수 있다(답 없음 질의). 단 값이 있다면 `ntt_ids`·`cve_ids`는 목록,
`query`는 문자열이어야 한다(JSON `null`이나 문자열 하나를 목록 자리에 넣는 것은 거부한다). 정답 공지가
카탈로그에 없거나, `split`이 `dev`/`test`가 아니거나, `id`가 중복이거나, CVE 형식이 틀리거나, 위 선택 필드의
타입이 틀리면 검사는 겹침 판정 대신 `ValueError`로 실패한다
(판정할 수 없는 입력은 통과시키지 않는다).

## 7. 경계조건 기대값

#12는 이 표를 테스트 기대값으로 그대로 쓴다. 표의 값은 소수 4자리 반올림이고 테스트 허용오차는
`abs=1e-4`다. 합성 입력만 쓴다(`d1`~`d9`는 문서 ID).

### 7.1 입력 규칙 (판정)

**판정**: 지표 함수는 **접힌 문서 순위 목록과 정답 집합만** 받는다. 점수는 받지 않는다. 동점 처리,
청크 -> 문서 접기는 지표 함수 앞단(하네스)의 일이다.

**이유**: 지표 함수가 동점 규칙을 몰라도 되므로 외부 구현(교차검증 대상)과 같은 입력으로 비교된다.

- `k <= 0`이면 `ValueError`. `ranked`에 같은 ID가 두 번 있으면 `ValueError`(하네스가 먼저 접어야 한다).
- `G`는 집합이다(중복 무시). 순위 목록이 k보다 짧으면 있는 만큼만 본다.

### 7.2 지표별 기대값 (answerable 질의: `G` 비어 있지 않음)

`ranked`는 문서 순위(1위부터), 모든 행의 k는 표에 적은 값이다.

| ID | 사례 | ranked | G | k | hit@k | recall@k | RR@k (MRR@k의 한 질의 값) | nDCG@k |
|---|---|---|---|---|---|---|---|---|
| B1 | 정답 1개, 1위 | d2 d7 d9 | {d2} | 3 | 1 | 1.0 | 1.0 | 1.0 |
| B2 | 정답 1개, 3위 | d7 d9 d2 | {d2} | 3 | 1 | 1.0 | 0.3333 | 0.5 |
| B3 | 복수 정답, 일부만 회수 | d7 d2 d9 | {d2, d4} | 3 | 1 | 0.5 | 0.5 | 0.3869 |
| B4 | 복수 정답, 전부 회수·이상적 순서 | d4 d2 d9 | {d2, d4} | 3 | 1 | 1.0 | 1.0 | 1.0 |
| B4b | 복수 정답, 전부 회수·2, 3위 | d7 d4 d2 | {d2, d4} | 3 | 1 | 1.0 | 0.5 | 0.6934 |
| B5 | `\|G\| > k` | d1 d2 d3 | {d1, d2, d3, d4} | 3 | 1 | 0.75 | 1.0 | 1.0 |
| B6 | 정답이 k 밖(4위, k=3) | d7 d8 d9 d2 | {d2} | 3 | 0 | 0.0 | 0.0 | 0.0 |
| B6b | 같은 순위, k를 4로 | d7 d8 d9 d2 | {d2} | 4 | 1 | 1.0 | 0.25 | 0.4307 |
| B7 | 목록이 k보다 짧음 | d7 d2 | {d2} | 5 | 1 | 1.0 | 0.5 | 0.6309 |
| B8 | **빈 검색 결과** | (빈 목록) | {d2} | 3 | 0 | 0.0 | 0.0 | 0.0 |

설명:

- B3: hit와 recall이 갈린다(2절). nDCG: DCG = 1/log2(3) = 0.6309, IDCG = 1 + 1/log2(3) = 1.6309.
- B5: 정답이 4개이고 k=3이므로 recall@3의 상한이 3/4 = 0.75다. nDCG는 `IDCG = min(4,3)`개 항이라
  완벽한 순위가 1.0이다.
- B8 **(빈 검색 결과)**: 정답이 있는 질의에서 빈 결과는 실패이므로 **0점으로 평균에 포함**한다. 건너뛰지
  않는다. 오류(예외, 시간 초과)로 결과를 못 받은 경우는 빈 결과가 아니라 실행 실패이므로 평균에 0으로
  넣지 말고 실행을 실패 처리한다.

### 7.3 답 없음 질의 (`G` 비어 있음)

| ID | 사례 | ranked | G | k | hit@k | recall@k | RR@k | nDCG@k | 평균에 포함? |
|---|---|---|---|---|---|---|---|---|---|
| N1 | 답 없음, 결과 있음 | d7 d2 | {} | 3 | `None` | `None` | `None` | `None` | **아니오** |
| N2 | 답 없음, 빈 결과 | (빈 목록) | {} | 3 | `None` | `None` | `None` | `None` | **아니오** |

**판정**: 정답이 없는 질의에서 hit·recall·MRR·nDCG는 **정의되지 않으므로 `None`을 돌려주고 평균에서
제외**한다. 0으로도 1로도 세지 않는다. 보고에는 `n_scored`(평균에 들어간 질의 수)와 `n_skipped`를 함께
적는다. **이유**: 0으로 넣으면 "답이 없는 걸 못 찾음"이 실패로 기록되어 올바른 동작이 감점되고, 1로 넣으면
아무것도 안 해도 점수가 오른다. 순위 지표는 "정답을 위쪽에 놓았는가"를 재는 것이어서 정답이 없으면 잴
대상이 없다.

답 없음 질의는 별도 지표 `abstain`으로 잰다. 검색 단계의 기권 정의: **1위 점수 < τ이거나 결과가 비어
있으면 기권(1)**, 아니면 0이다(경계는 `<`, 점수가 τ와 같으면 기권하지 않음).

- `abstain_rate` = `no_answer` 질의의 `abstain` 평균 (높을수록 좋음)
- `false_abstain_rate` = 정답이 있는 질의의 `abstain` 평균 (낮을수록 좋음)
- τ는 검색기마다 점수 척도가 달라 검색기별로 **dev에서만** 고르고 test에는 그대로 적용한다.

| ID | 사례 | 1위 점수 | τ | abstain |
|---|---|---|---|---|
| A1 | 1위 점수가 τ보다 낮음 | 0.42 | 0.5 | 1 |
| A2 | 1위 점수가 τ와 같음 | 0.50 | 0.5 | 0 |
| A3 | 빈 결과 | (없음) | 0.5 | 1 |

생성 단계에서의 답 없음 처리(답변 거부의 정확성)는 M5 범위이며 이 규약은 검색 단계 기권만 다룬다.

### 7.4 동점 순위

**판정**: 동점은 하네스가 `(-score, doc_id)` 오름차순으로 정렬해 **결정적으로** 깬다(`doc_id`는 문자열
사전순, `nttId`는 자릿수가 같아 정수 순과 같다). 지표 함수가 보는 `ranked`는 이미 이 정렬을 거친 목록이다.
보고하는 각 k(1, 5, 10)에 대해 순위 k위와 k+1위의 점수가 같은 질의 수를 `tie_at_cutoff@k`로 보고한다.
하네스는 정렬한 **전체 목록**을 지표 함수에 넘기고, k로 자르는 일은 지표 함수가 한다(7.1).

**이유**: 실행마다 순서가 달라지면 같은 설정이 다른 점수를 낸다(재현 불가). 낙관적(정답 먼저) 또는 비관적
(정답 나중) 정렬은 정답 라벨을 알아야 하므로 지표 함수가 점수를 받게 만든다. 사전순 id 규칙은 정답 라벨과
무관해 편향이 없다고 가정한다(검증되지 않은 가정이므로 `tie_at_cutoff@k`를 보고해 영향을 가시화한다).

| ID | 사례 | 점수 | G | k | 하네스가 만드는 ranked | hit@k | RR@k | nDCG@k |
|---|---|---|---|---|---|---|---|---|
| T1 | 동점 두 문서, 정답이 사전순 앞 | d2=0.8, d7=0.8, d9=0.5 | {d2} | 3 | d2 d7 d9 | 1 | 1.0 | 1.0 |
| T2 | 같은 입력, 정답이 사전순 뒤 | d2=0.8, d7=0.8, d9=0.5 | {d7} | 3 | d2 d7 d9 | 1 | 0.5 | 0.6309 |
| T3 | 동점이 컷오프를 가로지름 | d2=0.8, d7=0.8 | {d7} | 1 | d2 d7 (전체 목록, 지표 함수가 k=1로 자름) | 0 | 0.0 | 0.0 |

T3은 `tie_at_cutoff@1`에 1건으로 집계된다(1위와 2위 점수가 같다). 청크 -> 문서 접기 예: 청크 순위 `d2#c1(0.9) d7#c3(0.8)
d2#c4(0.7)`는 문서 순위 `d2 d7`이다(첫 등장만 남김).

### 7.5 ANN recall 기대값

| ID | 사례 | Exact_k | ANN_k | k | ann_recall@k |
|---|---|---|---|---|---|
| R1 | 일부 일치 | c1 c2 c3 | c1 c3 c9 | 3 | 0.6667 |
| R2 | ANN이 k개를 못 채움 | c1 c2 c3 | c1 | 3 | 0.3333 |
| R3 | ANN 결과 비어 있음 | c1 c2 c3 | (빈 목록) | 3 | 0.0 |
| R4 | 코퍼스가 k보다 작음(Exact가 2개뿐) | c1 c2 | c1 c2 | 3 | 1.0 |

분모는 `|Exact_k|`(전수 검색이 실제로 돌려준 개수, 최대 k)다. 답 없음 질의도 평균에 포함한다(레이블이
필요 없는 지표이기 때문).

### 7.6 평균 계산

| 규칙 | 값 |
|---|---|
| 질의 평균 | 정의된(`None`이 아닌) 질의만 산술평균. 빈 결과는 0으로 포함 |
| 예: nDCG@10이 1.0, 0.5, 빈 결과, 답 없음 4질의 | (1.0 + 0.5 + 0.0) / 3 = 0.5, `n_scored=3`, `n_skipped=1` |
| 유형별 평균과 macro | 유형별 평균 1.0(n=2), 0.4(n=5), 0.2(n=3)이면 macro = 0.5333, 질의 수 가중 = 0.46 |
| 채점 질의 0건인 유형 | 유형별 평균 1.0(n=2), 0.4(n=5), (n=0)이면 macro = (1.0 + 0.4) / 2 = 0.7. 분모는 채점 질의가 1건 이상인 유형 수 |

대표 값은 macro(0.5333)로 보고한다(5절).

### 7.7 수치 예시: 표 읽는 법

B3 계산: ranked `d7 d2 d9`, G = {d2, d4}, k=3. top_3 안의 정답은 d2 하나이므로 hit=1, recall=1/2=0.5,
첫 정답 순위 2라 RR=0.5. DCG는 2위에 1이 있어 `1/log2(3) = 0.6309`, IDCG는 정답 2개를 1, 2위에 놓았을 때의
`1 + 0.6309 = 1.6309`이므로 nDCG = 0.3869.

## 8. 청크 정답 파생 절차

1절의 판정은 문서 단위이므로 청크 정답은 채점 기준이 아니다. 다만 M3 청킹 실험과 M5 생성 평가는
청크 단위 정답이 필요하다. 이를 위해 **문서 단위 후보에서 청크 정답으로 내리는 절차**를 고정한다.

**판정**: 청크 정답은 청크 ID로 저장하지 않고, 교차 판정에서 두 판정자가 지정한 **근거 구간(evidence span)**에서
청킹 설정마다 코드로 파생한다.

**이유**: 청크 경계는 KISA 본문이 있어야 정해지고 1단계(후보 생성)는 본문을 읽지 않는다. 또 청킹 설정이 바뀌어도
근거 구간은 그대로 쓰이므로 정답을 다시 만들 필요가 없다.

| 단계 | 담당 | 입력 -> 출력 | 본문 접근 |
|---|---|---|---|
| 1. 후보 생성 | #27 (자동) | 공개 메타데이터 + CVE 조인 -> `candidate` 레코드: 질의, 유형, 후보 공지 `nttId` 목록(CVE 질의는 CVE -> 인용 공지 매핑 결과), 출처(`cve-join` 등). 청크 ID 없음 | 없음 |
| 2. 교차 판정 | #10 (판정자 A·B, 서로 결과를 보지 않음) | 후보 공지의 로컬 캐시 본문을 각자 읽고 관련성 라벨과 질의에 답하는 구간을 지정 -> `evidence = {nttId, parser_version, start, end}` (정규화 본문 문자 오프셋, 반개구간 `[start, end)`)와 판정 이유 | 로컬 캐시에서 읽고, 판정용 외부 모델 API 2종에 전송 |
| 3. 정답 확정 | #10 (일치 필터) | 관련성 라벨이 일치(둘 다 relevant)하고 근거 구간이 있는 후보 공지만 `gold`로 `G`에 확정. 갈리거나 근거가 없으면 `unjudged`, 잘리지 않은 본문에서 일치 not_relevant이면 비관련 | 로컬 캐시만 |
| 4. 청크 정답 파생 | 코드 | 청킹 설정의 청크 `c = (nttId, c_start, c_end)`가 정답이려면 같은 `nttId`의 근거 구간 `[e_start, e_end)`와 1자 이상 겹친다: `c_start < e_end and e_start < c_end` | 로컬 캐시만 |

규칙:

- `parser_version`은 `fixtures/kisa/manifest.json`의 값이다. 파서가 바뀌면 본문 오프셋이 달라지므로
  오프셋을 다시 대응시켜야 한다.
- 공개 리포에 두는 골든셋 레코드는 `nttId`·오프셋·판정 이유(고정 코드, 본문 인용 없음)만 가진다.
  본문 발췌를 넣지 않는다(`LICENSES/README.md`).
- 관련성 라벨이 일치한 뒤 근거 구간은 두 판정자의 유효 구간을 모두 보존한다(한쪽 구간으로 줄이지 않는다). 유효 구간 =
  정규화 본문 안에 들어오는 오프셋.
- kappa는 일치 필터 전에, 유효한 A·B 이진 라벨 쌍 전체로 계산한다(일치한 쌍만으로 계산하지 않는다). 정의되지 않으면
  (예: 유효한 쌍이 없거나 기대 일치가 1) 값을 `null`로 두고 사유를 남긴다.
- 겹침 임계값을 1자로 두는 이유: 근거 구간을 가로지르는 청크는 근거 일부를 담고 있어 생성에 쓸모가 있다.
  임계값(예: 50% 겹침)을 두면 그 값이 청킹 실험의 숨은 변수가 된다.
- 청크 단위 hit/recall/MRR/nDCG는 2, 3절과 정의가 같고 `ranked`가 청크 ID 목록이며 접기는 하지 않는다.
  **청킹 설정 간 비교는 문서 단위 지표로 한다**: 청크 수가 설정마다 달라 청크 recall의 분모가 달라지기
  때문이다. 청크 단위 지표는 M3·M5의 보조 보고로만 쓴다.
- 1단계는 #27, 2~3단계는 #10 교차 판정 몫이고 4단계는 코드가 파생한다. #27 후보 산출물은 v1 그대로이고
  교차 판정·채점 결과부터 v2를 쓴다.

## 11. 평가 트랙

평가는 두 트랙으로 나눈다. 두 트랙 모두 1절의 채점 규칙(`gold`/`unjudged`/비관련, condensed list, `excluded`)과
2~4·7절의 지표를 그대로 쓴다. 다른 것은 문서 단위와 정답의 출처다.

| 항목 | KISA 트랙 | 공개 트랙 |
|---|---|---|
| 문서 단위 | KISA 공지(`nttId`) | NVD CVE 레코드 id (`CVE-YYYY-NNNN+`) |
| 코퍼스 접근 | 본문이 로컬 캐시에만 있어 캐시가 있는 환경에서만 실행 | `fixtures/nvd`만 필요, 새 클론에서 재현 |
| 정답 출처 | 두 판정자의 교차 판정(`gold`, #10) | fixture 메타데이터에서 기계적으로 정함, LLM 판정 없음(질의셋 #35) |
| `unjudged` | 판정이 갈림, 근거 없음, 잘린 본문의 not_relevant 등 | 메타데이터 절단(예: CPE 절단)으로 판정할 수 없는 문서 |
| 판정 묶음 밖 | 비관련으로 간주(풀링 평가, 1절 한계) | 정답 규칙(#35)에서 `gold`·`unjudged`가 아닌 문서는 비관련 |
| 본문 전송 | 판정용 외부 모델 API 2종으로 전송(`LICENSES/README.md`) | 없음 |

- 질의 유형(5절)과 `no_answer`의 기계적 부재 확인은 두 트랙에 모두 적용한다. 공개 트랙의 부재 확인 대상과 방법,
  공개 트랙에서 만들지 않는 유형은 질의셋(#35)이 정한다.
- 분할(6절)도 두 트랙에 같다. 공개 트랙은 #35의 매핑(질의 항목 `item`과 문서 목록 `notice`, 6절 검사 입력 형식)으로
  `splits.assert_disjoint`를 쓰고, `vendor:product` 그룹은 #35가 직접 검사한다. 공개 트랙의 dev 비율 기준은 질의 수 기준 **30~50%**(목표 40%, ±10%p)다.
- 두 트랙의 지표는 문서 단위와 정답 출처가 달라 서로 합산하거나 같은 표의 한 열로 비교하지 않는다. 트랙별로
  따로 보고한다.
