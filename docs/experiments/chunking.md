# 청킹 실험 (`chunking`)

결과: 주 트랙(KISA)은 `hypothesis-rejected`다. test macro nDCG@10은 dense 베이스라인보다 +0.0654 높지만 95% 구간 [-0.0082, +0.1510]의 하한이 0 아래라 판정 규칙상 기각이다. 사전 등록한 격자에서 dev로 설정을 고르고 test를 한 번 돌렸으며 결과를 본 뒤 설정·가설·판정 규칙을 바꾸지 않았다. 하네스 계약은 [README.md](README.md), 판정 규칙의 정본은 런 스펙 이슈 #43의 "실험 공통 규칙"이다.

## 1. 가설 (사전 등록)

- 가설: KISA 공지를 청크로 나눠 bge-m3로 인코딩하고 문서 점수를 청크 점수의 최댓값으로 두면, 문서 하나를 한 벡터로 만드는 dense 베이스라인보다 test macro nDCG@10이 높다.
- 주 트랙: KISA 트랙, 기준 = `results/baselines/kisa/dense.jsonl`. 공개 트랙은 NVD 설명문이 짧아 청킹이 거의 바뀌지 않으므로 판정하지 않고(실험 변형이 없다) 청크가 2개 이상인 레코드 수만 적는다(4.7절).
- 파싱 고정: 본문은 `load_cached_body`가 돌려준 정규화 본문(`fixtures/kisa/manifest.json`의 `parser_version` `kisa-html-v1`) 그대로다. 파서·정규화를 바꾸지 않고 바뀌는 것은 청크 경계뿐이다.
- 판정: test macro nDCG@10의 `delta = 실험 - 기준`이 0보다 크고, 유형별 층화 paired bootstrap(10000회, 시드 `20261029`) 95% 구간의 하한이 0보다 크면 `hypothesis-confirmed`, 그 밖은 `hypothesis-rejected`.
- 판정은 문서 단위 지표로만 한다(eval-protocol 8절: 청크 수가 설정마다 달라 청크 단위 recall의 분모가 다르다). 청크 단위 hit@10은 보조 보고다.

## 2. 구성

- 색인 텍스트: 공지 제목 + 줄바꿈 + 정규화 본문(기준선과 같다). 제목은 첫 청크에만 들어간다.
- 청크: bge-m3 토크나이저(모델과 같은 revision)로 색인 텍스트 전체를 한 번 토큰화(특수 토큰 제외)하고, 토큰 `size`개 창을 `size - overlap` 간격으로 민다. 마지막 창이 텍스트 끝에 닿으면 멈추므로 마지막 청크는 짧을 수 있고, 텍스트가 한 창보다 짧으면 청크 1개다. 청크의 문자 구간은 첫 토큰 시작 ~ 마지막 토큰 끝(반개구간)이고 첫 청크는 0에서, 마지막 청크는 텍스트 끝에서 끝난다. 인코딩할 때 청크 텍스트가 다시 토큰화되므로 특수 토큰 2개가 더해진다.
- 청크 ID: `<nttId>#<색인 텍스트 문자 시작>-<끝>`(반개구간)으로 오프셋만 담는다.
- 모델: 기준선과 같다. `BAAI/bge-m3` revision `5617a9f61b028005a4858fdac845db406aefb181`, dense 출력만, CLS pooling, L2 정규화, float32, CPU. `baselines.dense.build_dense_index`를 청크 텍스트에 쓴다. 질의는 청크 인덱스와 같은 모델로 인코딩한다(질의 형식은 기준선과 같다).
- 문서 점수: 그 문서 청크 점수(정규화 벡터 내적)의 최댓값. 후보는 코퍼스 전체 문서(모든 문서가 청크를 하나 이상 가진다). 순위·unjudged 제거·상위 100건 저장은 기준선과 같은 공통 채점 코드가 한다.
- 격자(dev에서 고름, 6개): 크기 {256, 512, 1024} x 겹침 {0, 크기의 1/8}. 선택 규칙은 하네스 기본값(dev macro nDCG@10 최대, 같으면 격자 순서에서 앞선 설정)이고 격자 순서는 `256/0, 256/32, 512/0, 512/64, 1024/0, 1024/128`이다. 라벨은 `크기/겹침`(토큰)이다.
- τ(no_answer 기권 임계값): 기준선과 같은 규칙(dev에서 abstain_rate - false_abstain_rate 최대, 같으면 가장 낮은 τ)으로 문서 점수의 원래 1위 점수에 대해 dev에서 고른다.
- 보조 보고(청크 단위, 판정에 쓰지 않는다): 골든셋 `answers[].evidence`(정규화 본문 오프셋, 두 판정자 구간 전부)를 제목 길이 + 1만큼 밀어 색인 텍스트 오프셋으로 바꾸고, 정답 문서의 청크 중 1자 이상 겹치는 청크를 정답 청크로 본다. 청크 순위는 청크 점수 내림차순 전체 순위에서 그 질문의 unjudged 문서 청크를 지운 목록이고(접기 없음) hit@10은 질문별 값을 유형별로 평균한 뒤 유형 단순 평균(macro)한다.

## 3. 재현 명령

`<KISA-ROOT>`는 KISA 캐시(`data/kisa`)가 있는 체크아웃이다. 모델이 필요한 실행은 `embed` 그룹을 쓴다. 측정은 `OMP_NUM_THREADS=4`로 했다.

```
uv sync --locked --group embed
OMP_NUM_THREADS=4 uv run --no-sync python scripts/run_experiment.py --exp chunking --track kisa --kisa-root <KISA-ROOT> --split dev --out-dir <빈 디렉터리>   # 격자·τ 확인(몇 번 돌려도 됨, 커밋된 결과를 건드리지 않는다)
OMP_NUM_THREADS=4 uv run --no-sync python scripts/run_experiment.py --exp chunking --track kisa --kisa-root <KISA-ROOT>   # dev 선택 뒤 test 1회, results/experiments/chunking에 쓴다
uv sync --locked --dev
uv run python scripts/run_experiment.py --exp chunking --compare   # 모델·KISA 캐시 없이 저장본에서 metrics·comparison을 다시 계산해 대조(불일치 exit 1)
```

산출물: `results/experiments/chunking/kisa/chunk_max.jsonl`, `manifest.json`, `metrics.json`, `comparison.json`. test 설정 해시는 manifest의 `runs["kisa/chunk_max"].test.config_hash`다. 청크 순위 파일은 저장하지 않는다. 이 문서의 4.3절 청크 단위 값과 4.6절 색인 시간은 모델 실행 때의 관측값으로 manifest의 `description`에만 있고 `--compare`가 다시 계산하지 않는다(문서 단위 지표와 판정만 다시 계산한다). 이 실험의 dev 전용 실행을 빈 `--out-dir`에 한 번 먼저 돌렸고(저장하지 않는 확인용), 그 격자 값이 아래 4.1절과 같았다.

## 5. 판정

- **주 판정(KISA 트랙): `hypothesis-rejected`.** delta +0.0654는 양수지만 95% 구간 [-0.0082, +0.1510]의 하한이 0 아래라 청크 최댓값이 dense 베이스라인보다 높다고 주장할 수 없다. 하한이 0에 가깝고 점추정치와 `cve_explicit` 개선(+0.1962)은 모두 양의 방향이다. 이 표본(test 23건)으로는 효과가 있다는 것도 없다는 것도 확정하지 못한다.
- 결과가 가설을 기각해도 정상 종료다. 이슈 라벨은 `comparison.json`의 `primary.verdict`대로 `hypothesis-rejected`다.

## 6. 실패 사례 분석

질문 문장과 문서 본문은 쓰지 않고 질문 ID만 쓴다. 순위는 저장된 condensed 상위 100건 안의 첫 정답 순위다(전부 100위 안이라 "범위 밖"은 없다). 아래 "확인"은 저장된 결과 파일(기준선 dense 저장본과 이 실험의 저장본)과 토큰 수 같은 수치에서 직접 계산한 사실이고, "추정"은 그 사실로부터의 해석이다.

### 6.1 원인

- 확인: 변한 질문 6건이 모두 `cve_explicit`이다. 다른 두 유형은 기준선이 이미 1.0000이라 오를 곳이 없었고 청킹이 이를 깨지도 않았다.
- 확인: 개선 4건(표 순서)의 정답 문서는 모두 1024 토큰을 넘어(1362, 1056, 1063, 9280) 선택한 설정에서 청크가 2개 이상이다. 근거 구간은 14~106자로 짧고 시작 토큰은 각각 187, 254, 177, 4441번째다. 즉 근거는 짧은 구간이고 본문은 길다. 추정: 문서 전체를 한 벡터로 만들면 CVE를 인용한 짧은 구간이 긴 본문에 희석돼 순위가 낮고(기준선 순위 14~40), 청크로 나눠 최댓값을 쓰면 그 구간을 담은 청크가 높은 점수를 받아 오른다. 청크 점수의 내용(어느 청크가 최대였는지)은 저장하지 않아 이 설명은 순위 변화와 길이로부터의 추정이다.
- 확인: `g1-cve-2026-62817`의 정답 문서는 9280 토큰으로 8192를 넘지만 근거 시작이 4441번째 토큰이라 기준선의 절단(8192 이후)이 근거를 잘라 낸 것은 아니다(근거 길이가 14자라 끝도 8192 안이다). 이 질문의 개선(40위 -> 10위)은 절단 해소가 아니라 희석 완화와 일치한다(추정).
- 확인: 악화 `g1-cve-2026-53873`의 정답 문서는 235 토큰이라 어느 설정에서도 청크 1개이고, 그 청크는 문서 전체와 같은 텍스트다. 정답 문서의 점수는 기준선과 같은 0.559027이고 1위 점수(0.586569)도 같다. 그런데 순위가 7위에서 11위로 내려갔으므로 원인은 정답 문서가 아니라 다른 문서들이 청킹으로 점수를 얻어 정답 문서를 앞선 것이다. 추정: 긴 문서는 청크 중 하나만 질의와 잘 맞아도 점수가 오를 수 있는데 짧은 문서(청크 1개)는 점수가 그대로라, 짧은 정답 문서의 상대 순위가 내려갈 수 있다. 어느 문서가 정답을 앞섰는지는 이 질문에 대해 확인하지 않았다.
- 확인: 악화 `g1-cve-2026-14669`의 정답 문서는 2373 토큰이라 청크가 여러 개이고 정답 문서 점수가 0.593342에서 0.590079로 조금 내려갔다. 3위에서 5위로 내려간 것은 정답 문서 점수 하락과 다른 문서의 상승이 함께 만든 결과다. 어느 쪽이 더 컸는지는 순위 앞의 문서 점수를 이 질문에 대해 확인하지 않았다.
- 확인: test 질문 23건 중 정답 문서가 1024 토큰을 넘는 것은 8건이고 나머지 15건은 정답 문서가 청크 1개(문서 전체와 같은 텍스트)라 정답 문서 점수가 기준선과 같다(`g1-cve-2026-53873`에서 점수 일치를 직접 확인했다). 정답 문서의 점수가 달라질 수 있는 질문이 적어 효과를 보일 수 있는 표본이 더 작다.
- 확인: test 청크 단위 hit@10은 `cve_explicit` 0.3636으로 같은 유형의 문서 단위 hit@10(0.8182)보다 낮다. 추정: 문서가 상위에 오른 이유가 근거 구간 청크가 아니라 다른 청크(예: 제목이 들어 있는 첫 청크)일 수 있다. 근거와 겹치는 청크가 실제로 상위가 아니었다는 뜻이므로 청크 점수 기반 개선이 근거 구간 덕이라고 단정하지 않는다.
- 확인: dev에서는 선택 설정 1024/128이 기준선(0.8802)보다 +0.0390 높았고 test는 +0.0654로 방향이 같다. 다만 dev 격자 안에서 설정마다 순위가 바뀌어(512/0은 기준선보다 낮은 0.8623) 설정 선택의 안정성은 확인하지 못했다.

## 7. 한계

- 질문 단위 재표집은 test 안 질문끼리의 의존(같은 공지·CVE를 쓰는 질문)을 독립으로 다뤄 구간을 실제보다 좁게 낼 수 있다. dev와 test 사이는 eval-protocol 6절의 그룹 분할로 이미 분리돼 있다.
- KISA test는 정답이 있는 질문 23건이고 `explanation_comparison`(5건)과 `product_symptom`(7건)은 n_scored < 10이라 유형별 우열을 주장할 수 없다. 변화는 `cve_explicit` 11건 중 6건에서만 나타났고 구간이 넓다([-0.0082, +0.1510]).
- dev 정답 질문이 19건이라 6개 격자 사이의 차이는 질문 한두 개 수준이다. 선택은 규칙대로 했지만 이 격자 안의 설정 사이에서 test 결과가 안정적이라고 확인한 것은 아니고, test는 선택한 설정 하나만 돌았다.
- 첫 정답 순위는 저장된 상위 100건 안의 순위다. 이번 비교의 모든 정답이 100위 안에 있었다.
- 청크 크기는 토큰화 한 번의 토큰 수 기준이고 청크 텍스트를 다시 인코딩할 때 특수 토큰이 더해져 모델이 보는 길이는 크기 + 2 안팎이다. 제목은 첫 청크에만 있다. 청크 점수 합산은 최댓값 하나만 측정했고(합산 방식 비교, BM25 청킹, 문장·구조 기반 청킹, 파서 개선은 범위 밖), 청크 크기 격자는 6개다.
- 청크 단위 hit@10과 색인 시간은 모델 실행 때의 관측값이라 `--compare`가 다시 계산하지 않는다. 기본 경로에 `--split dev`를 다시 돌리면 manifest `description`이 그 실행의 관측(dev만)으로 다시 쓰여 test 청크 hit@10이 빠진다. 그래서 확인용 재실행은 빈 `--out-dir`에서 한다.
- 시간 수치는 같은 맥에서 다른 실험과 병렬로 돌았을 수 있어 참고값이다. dense 인덱스는 설정마다 새로 만들고(한 번에 하나만 메모리에 둔다) 선택된 설정은 test를 위해 한 번 더 만들었다. 같은 모델·시드·배치라 결과는 같다.
- 이 결과는 "고정 길이 토큰 청크 + bge-m3 dense + 최댓값 집계" 하나에만 해당한다.
